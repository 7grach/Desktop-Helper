# Совместная работа двух агентов

Документ описывает, как два AI-агента работают с одним репозиторием с разных компьютеров. Инструкция не зависит от локальных путей: каждый агент клонирует репозиторий к себе.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| **Агент A** | первый агент / интегратор | берёт задачи `A-*`, проверяет и мержит PR в `develop`, пушит `develop`, ведёт `docs/TASKS.md` |
| **Агент B** | второй агент (другой компьютер) | берёт задачи `B-*`, работает в своей ветке, открывает PR в `develop`, не мержит |

Пользователь ставит задачи и принимает решение при конфликте приоритетов. Если задачи нет, агент может предложить её в своей секции `docs/TASKS.md` со статусом `PROPOSED`, но не начинает работу без перевода в `TODO`.

## Предложения задач

Оба агента могут создавать задачи, но с ограничениями:

- Новую задачу агент добавляет **только в свою секцию** `docs/TASKS.md` со статусом `PROPOSED`.
- `PROPOSED` — это идея, а не разрешение начинать.
- В `TODO` задачу переводит пользователь или Агент A после согласования.
- Если Агент B нашёл проблему в зоне Агента A (например, в `package.json` или `src/main.js`), он не редактирует секцию A, а добавляет `PROPOSED` в свою секцию с пометкой «для A». Агент A переносит её в свою секцию.
- Агент A просматривает `PROPOSED` при планировании следующего шага и согласует приоритеты с пользователем.

Так у обоих агентов есть право предлагать, но никто не начинает несогласованную работу и не назначает задачи другому агенту.

## Ветки

```text
main        — стабильная версия
develop     — интеграционная ветка, сюда попадают проверенные задачи
  ├── agent-a/<task-id>   — ветки Агента A
  └── agent-b/<task-id>   — ветки Агента B
```

Правила:

- В `main` и `develop` не коммитить напрямую.
- Ветка задачи создаётся от свежего `origin/develop`.
- Одна задача — одна ветка и один PR.
- Долгоживущих личных веток нет: после мержа ветку задачи можно удалить.

## Первый запуск на новом компьютере

```powershell
git clone https://github.com/7grach/Desktop-Helper.git
cd Desktop-Helper
git switch develop
git pull origin develop
npm install
npm start
```

Если у вас нет прав на push в `7grach/Desktop-Helper`, сделайте fork и работайте в нём:

```powershell
git clone https://github.com/<ваш-логин>/Desktop-Helper.git
cd Desktop-Helper
git remote add upstream https://github.com/7grach/Desktop-Helper.git
git fetch upstream
git switch -c agent-b/B-1 upstream/develop
```

PR в этом случае открывается из вашего fork в `7grach/Desktop-Helper:develop`.

Если npm 12 не установил Electron и `electron.exe` отсутствует:

```powershell
node node_modules\electron\install.js
```

Проверка:

```powershell
node --test tools/test-file-help.js
node --test tools/test-screen-capture.js
```

`tools/test-ai-settings.js` на Windows пока даёт 5 падений из-за POSIX-путей в тестовом харнессе — это известная проблема, её исправляет Агент A в задаче `A-1`.

## Цикл задачи

1. Прочитать `docs/TASKS.md` и взять свою задачу. Если подходящей нет — добавить `PROPOSED` в свою секцию и дождаться перевода в `TODO`.
2. Поставить в своей секции `IN PROGRESS`, указать ветку и дату.
3. Создать ветку:
   ```powershell
   git fetch origin
   git switch -c agent-b/B-1 origin/develop
   ```
4. Работать небольшими коммитами. Как можно раньше открыть **draft PR** в `develop`.
5. Перед review:
   ```powershell
   git fetch origin
   git rebase origin/develop
   node --test tools/test-file-help.js
   node --test tools/test-screen-capture.js
   ```
6. Запушить ветку:
   ```powershell
   git push -u origin agent-b/B-1
   ```
7. Поставить `REVIEW`, указать commit и результаты проверки.
8. Агент A проверяет PR, мержит в `develop`, пушит `develop`, ставит `DONE`.
9. Агент B после `DONE` делает `git fetch origin` и `git rebase origin/develop` перед следующей задачей.

## Статусы в docs/TASKS.md

- `PROPOSED` — идея агента, не согласована; начинать нельзя.
- `TODO` — задача согласована и назначена, но не начата.
- `IN PROGRESS` — агент работает; указана ветка.
- `REVIEW` — ветка запушена, PR открыт, нужна проверка.
- `BLOCKED` — нужна помощь пользователя или другой агент занял пересекающиеся файлы.
- `DONE` — PR смержен в `develop`.
- `BACKLOG` — идея на будущее, не начинать без команды.

Каждый агент редактирует только свою секцию. Чужие строки не переставлять и не переписывать.

## Границы файлов

Чтобы не ловить конфликты, задачи делятся по файлам, а не «по всему проекту»:

- `A-1`: `tools/test-ai-settings.js`, `package.json`, `.github/workflows/`.
- `B-1`: `README.md`, `DEMO.md`.
- Если задача требует общий файл (`app.js`, `coach.js`, `i18n.js`, `package.json`), сначала согласуйте порядок: один делает, второй ждёт.

Если оба агента одновременно меняют один файл — второй должен остановиться, поставить `BLOCKED` и написать пользователю.

## Проверка PR (Агент A)

- Ветка от свежего `origin/develop`.
- В PR только файлы задачи.
- Тесты проходят; известные падения описаны.
- Нет `node_modules`, `assets/vosk`, `team.json`, `dist`.
- `docs/TASKS.md` обновлён в своей секции.
- После мержа: `git push origin develop`, статус `DONE`.

## Коммиты и PR

- Коммиты: `test: ...`, `docs: ...`, `fix: ...`, `feat: ...`.
- PR называть по задаче: `[A-1] Windows tests + npm test + CI`.
- В описании PR: что изменено, как проверено, ссылка на задачу.
- Draft PR можно открыть сразу после первого коммита — это сигнал второму агенту, что задача в работе.

## Безопасность

- Не коммитить `team.json`, API-ключи, `.env`, `node_modules`, `assets/vosk`, `dist`.
- Не публиковать личные ключи в PR и issue.
- `npm audit fix --force` не запускать: можно сломать `electron-builder`.
